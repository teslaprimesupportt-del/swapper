    44→## 1.1 Product
    45→
    46→A browser-first realtime AI media studio where a user can open a camera and microphone, choose a visual transformation and voice transformation, and see/hear the transformed result continuously with low latency.

    56→        ├──> Capture ──> Realtime Media Transport ──> Session Gateway
    57→Mic ────┘                                      │

    61→                                               └──> Control/Prompt Pipeline

    63→                                                        ▼

    65→                                                        │
    66→                                                        ▼

   224→# 4. CORE USER JOURNEYS
   225→
   226→## Journey A — First realtime session
   227→
   228→1. User opens Studio.
   229→2. Browser requests camera/microphone permissions.
   230→3. Device selection appears.
   231→4. Local preview starts immediately.
   232→5. User selects a transformation.
   233→6. Backend creates a short-lived realtime session token.
   234→7. WebRTC session establishes.
   235→8. AI provider connection establishes.
   236→9. Output begins.
   237→10. Metrics appear.
   238→11. User can change transformation without leaving the session.
   239→
   240→## Journey B — Voice changer
   241→
   242→1. User enables microphone.
   243→2. Audio capture begins.
   244→3. Noise suppression and preprocessing run.
   245→4. Audio is streamed.
   246→5. Voice conversion processes the stream.
   247→6. Converted audio returns.
   248→7. Output is synchronized with video.
   249→8. User can switch voice presets during the session.
   250→
   251→## Journey C — Reference transformation
   252→
   253→1. User uploads reference image.
   254→2. Backend validates and stores it temporarily.
   255→3. Reference is converted to a secure temporary URL/provider asset.
   256→4. User enters prompt.
   257→5. Transformation request is compiled.
   258→6. Realtime session receives the update.
   259→7. Output changes without restarting unnecessarily.
   260→
   261→## Journey D — Network failure
   262→
   263→1. WebRTC connection degrades.
   264→2. Client detects quality degradation.
   265→3. UI displays reconnecting state.
   266→4. Session coordinator attempts bounded reconnection.
   267→5. Existing session state is restored if possible.
   268→6. If unavailable, provider failover/degraded mode activates.
   269→7. User receives a clear status.

   871→## 19.1 Voice Clone Verification Requirement (VOICE-CONSENT-001)
   872→
   873→This subsection converts the general "must include consent/authorization controls" requirement in §59 into concrete, implementable verification steps. It is mandatory for any feature that creates a `VoicePreset` from a user-supplied voice sample (a clone), as distinct from a purely synthetic/built-in preset.
   874→
   875→A cloned voice may not be created or activated for use until all of the following pass:
   876→
   877→| Step | Requirement |
   878→|---|---|
   879→| Rights attestation | The uploading user affirmatively attests, per clone, that the voice belongs to them or that they hold documented rights/consent to clone it. Store this attestation as an immutable record tied to the `VoicePreset` row, not just a one-time checkbox at signup. |
   880→| Liveness/active-consent capture | Require the source sample to be captured live within the product (e.g. read a randomized on-screen consent phrase), rather than accepting an arbitrary pre-recorded upload with no provenance. This raises the bar against cloning a voice the uploader does not control. |
   881→| Consent artifact retention | Retain the consent capture (audio + attestation + timestamp) as an auditable artifact under the retention policy in §41, independent of the derived voice model itself. |
   882→| Revocation path | The consenting individual (if different from the account holder, e.g. an authorized third party) must have a documented path to revoke consent, which immediately disables the associated `VoicePreset`. |
   883→| Abuse/impersonation review | Cloned-voice presets are subject to the moderation/abuse-control requirements referenced in §26, with a defined escalation path for reported impersonation. |
   884→
   885→`UNVERIFIED` claims about what a specific competitor product does or does not support (§101.3) must never be used to justify weakening this requirement. This gate exists independent of what any other product implements, per Contract item 19 in §0.

  1110→## 24.1 Owner/Internal Billing Exemption (BILL-001)
  1111→
  1112→The platform must support a role-scoped billing exemption for internal/owner accounts, without weakening the server-authoritative usage model above.
  1113→
  1114→Requirements:
  1115→
  1116→- `users.role` (§23) includes an internal tier (e.g. `owner`, `internal`) distinct from standard `user`/`admin` roles.
  1117→- A per-account flag — e.g. `billingExempt: boolean` — determines whether usage events for that account are invoiced. This must be a data-level flag checked server-side, never a client-side or UI-level bypass.
  1118→- **Usage events are still recorded for exempt accounts.** Exemption affects invoicing only, not metering. The owner's real GPU/provider cost is not free to the business — it must still flow through `usage_events` and the cost model in §57 so actual spend stays visible.
  1119→- Exemption must be auditable: every exempt session is logged in `audit_logs` (§23) with actor, timestamp, and cost basis, so "free for me" never becomes an untracked liability.
  1120→- Exemption must not bypass the abuse/quota controls in §57 (max session duration, concurrency limits) — an unmetered account is not an unlimited one; without a ceiling, a compromised or misused owner session can still generate runaway provider cost.
  1121→- Feature flag: `billing_enforcement` (extends §42) is evaluated per-account, not globally, so standard pay-as-you-go billing for all other users is unaffected by the owner exemption.
  1122→
  1123→Every other account remains on the standard pay-as-you-go usage-event ledger defined above.
