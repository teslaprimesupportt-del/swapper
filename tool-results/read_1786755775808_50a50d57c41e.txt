  3809→# 101. CODE INTEGRITY AND CONTINUOUS EXECUTION PROTOCOL (CI-CEP)
  3810→
  3811→This section is binding on every phase defined in §50 and every acceptance gate defined in §51 and §52. It supersedes any earlier instruction that could be read as permission to produce shallow, generic, or unverified code, or to abandon a phase before its acceptance criteria are met. Where this section and an earlier section conflict on execution discipline, this section governs.
  3812→
  3813→Requirement IDs introduced here (`CI-xxx`) must be added to the Requirement Traceability Matrix in §80 like any other requirement.
  3814→
  3815→## 101.1 Definition: Generic/Sloppy Output (CI-001)
  3816→
  3817→Output is classified **NON-CONFORMANT** if any of the following are true. Non-conformant output cannot be reported as part of a completed phase under §51.
  3818→
  3819→| Class | Definition |
  3820→|---|---|
  3821→| Untraced boilerplate | Code copied from a generic pattern without being adapted to this repository's actual types, contracts, and provider-abstraction layers (§13, §70) |
  3822→| Unverified plausibility | Code that "looks correct" but was not checked against the real current state of the files it touches |
  3823→| Placeholder-as-final | TODOs, stubs, hardcoded fixtures, or fake success paths (violates Contract items 7–9 in §0) present in a path reported as complete |
  3824→| Silent scope narrowing | Code that satisfies the literal wording of a requirement while missing its functional intent |
  3825→| Orphaned change | Code with no traceable requirement ID (§80) or ADR (§81) justifying why it exists |
  3826→
  3827→Every artifact the agent writes must cite the requirement ID(s) and/or ADR ID(s) it implements. A change with no traceable justification is itself a defect.
  3828→
  3829→## 101.2 Verification Gate (CI-002)
  3830→
  3831→Every unit of work passes through two mandatory checkpoints. Neither may be skipped or merged into one.
  3832→
  3833→**Gate A — Pre-Implementation**
  3834→
  3835→| Step | Action |
  3836→|---|---|
  3837→| A1 | Inspect actual current repository state for every file to be touched (§0 item 2) |
  3838→| A2 | Reconcile intended change against real structure, types, and contracts — not memory of a similar system |
  3839→| A3 | Classify every non-trivial claim per the Zero-Guess Protocol (§101.3) before writing code that depends on it |
  3840→
  3841→**Gate B — Post-Implementation**
  3842→
  3843→| Step | Action |
  3844→|---|---|
  3845→| B1 | Re-read every changed file as written to disk, not as drafted |
  3846→| B2 | Check against the phase's stated `ACCEPTANCE CRITERIA` (§54) |
  3847→| B3 | Check against every PRD section the change implements |
  3848→| B4 | Verify integration points — types, imports, config keys, provider contracts — actually resolve |
  3849→| B5 | Verify no previously passing behavior regressed (§0 item 3) |
  3850→| B6 | Run the applicable tier of §38 tests before the phase may be reported complete |
  3851→| B7 | Produce a Gate B evidence log — commands run, raw output, files diffed, tests executed with results — and attach it to the phase report (§54). A self-report of "Gate B passed" with no attached evidence does not satisfy B7 (see §101.9). |
  3852→
  3853→Code is not "done" because it was generated. It is done only after passing Gate B. A phase report (§54) submitted without an attached Gate B evidence log is itself non-conformant and cannot satisfy Definition of Done item 12 (§51).
  3854→
  3855→## 101.3 Zero-Guess Protocol (CI-003)
  3856→
  3857→Every non-trivial factual claim underlying a piece of code must be classified before that code is written:
  3858→
  3859→| Label | Meaning | Permitted basis |
  3860→|---|---|---|
  3861→| `VERIFIED` | Confirmed against the actual repository, actual official documentation (§62), or an actual executed check | Direct inspection only |
  3862→| `ASSUMED` | Not yet confirmed; logged to the Assumption Register (§82) with confidence and impact-if-wrong | Explicit, tracked, reversible |
  3863→| `UNVERIFIED` | Flagged as such in the response; blocks phase completion until resolved | Never a basis for shipped code |
  3864→
  3865→Forbidden basis for writing code: pattern-matching to "what this API/library/file usually looks like" and presenting it as fact. This applies to API signatures, provider behavior, library interfaces, configuration keys, file paths, existing repository structure, and data shapes — no exceptions for "just one line." A single fabricated line is treated with the same severity as a fabricated subsystem, because the failure mode (undetected incorrect assumption in shipped code) is identical.
  3866→
  3867→**Fallout rule:** if an `ASSUMED` claim logged to the Assumption Register (§82) is later proven wrong, this is not a footnote-only correction. It automatically triggers a Non-Regressive Recovery Protocol re-derivation (§101.5) for the assumption itself and for every downstream artifact that was built depending on it, traced via the requirement/ADR IDs those artifacts cited under CI-001. An ADR update alone does not close the loop — the affected code must be re-verified against the corrected fact.
  3868→
  3869→## 101.4 Continuous Execution Guarantee (CI-004)
  3870→
  3871→Once a phase's scope is confirmed (§50, §54), the agent drives it to its stated acceptance criteria without discretionary interruption. The distinction that governs this section is **blocking condition** vs. **discretionary halt**:
  3872→
  3873→| Condition | Classification | Required response |
  3874→|---|---|---|
  3875→| Failing test, compile error, unexpected repo state | Expected operating condition | Diagnose and fix; continue (per §53's BREAK→FIX→VERIFY loop) |
  3876→| Ambiguous product decision with no safe default | Genuine blocker | Surface immediately per §77/§78; do not silently choose and do not silently stall |
  3877→| Missing credential/external dependency outside agent's control | Genuine blocker | Surface immediately, name exactly what is needed, continue on all unblocked work in parallel |
  3878→| Fatigue-style stopping, scope feels large, task feels tedious | Discretionary halt | **Prohibited.** Not a valid reason to pause, defer, or abandon a phase |
  3879→| Partial progress feels "good enough" | Discretionary halt | **Prohibited.** Only the stated acceptance criteria define done (§51) |
  3880→
  3881→Surfacing a genuine blocker is reporting, not stopping — the agent states what it needs and keeps working on everything not gated by that blocker. Silence, indefinite pausing, or unexplained abandonment mid-phase are not available responses under this protocol.
  3882→
  3883→## 101.5 Non-Regressive Recovery Protocol (CI-005)
  3884→
  3885→If a phase's acceptance criteria are not met by the end of an attempt, the failure is handled as data, not as a stopping point:
  3886→
  3887→1. **Report honestly** — state exactly what passed Gate B, what failed, and why, using the `KNOWN LIMITATIONS` field of §54's response format. Never mark a failed phase complete.
  3888→2. **Do not leave a half-verified state as the baseline** — an incomplete attempt must not be left implicit for a future attempt to inherit unexamined.
  3889→3. **Re-derive from ground truth on the next attempt** — re-run Gate A against the repository's actual current state rather than resuming from the previous attempt's assumptions. If the previous attempt's partial work is inconsistent with what Gate A now finds, treat it as unverified and rebuild the affected portion rather than patching over it.
  3890→4. **Do not repeat the same unverified work indefinitely** — each retry must be demonstrably different from the last: a new fact was verified, a blocker was resolved, an assumption was corrected. A retry that changes nothing about what was previously wrong is not a valid retry.
  3891→5. **Retry ceiling** — after **three** re-derivation attempts on the same requirement ID without meeting acceptance criteria, the requirement automatically escalates to a `BLOCKED — HUMAN DECISION REQUIRED` state rather than attempting a fourth retry. Escalation must state: what was tried across all three attempts, what changed each time, and the specific decision or resource needed to proceed. A subsystem-specific ADR (§81) may set a different ceiling with explicit justification; absent one, three is the default.
  3892→
  3893→The objective of CI-005 is that every attempt starts from verified ground truth rather than compounding an earlier, unverified mistake — not endless unmonitored looping, and not silent abandonment.
  3894→
  3895→## 101.6 Hallucinated-Dependency Check (CI-006)
  3896→
  3897→A distinct and common failure mode from general guessing (§101.3): inventing a dependency that does not exist. Before any import, package install, API endpoint, or config flag is used, the agent must confirm — not assume — that it is real:
  3898→
  3899→| Dependency type | Required confirmation |
  3900→|---|---|
  3901→| npm/pip/other package | Confirm the package name, version, and published API actually exist in the registry (§48's package boundaries apply) — not "a package like this probably exists" |
  3902→| External API endpoint | Confirm the endpoint exists in current official documentation (§62), not a remembered or inferred URL pattern |
  3903→| Config/environment flag | Confirm the flag is real for the specific library/service version in use, not a plausible-sounding name |
  3904→| Framework API/method | Confirm the method exists on the specific version pinned in this repository, not a version remembered from training |
  3905→
  3906→A hallucinated dependency is classified as an `UNVERIFIED` claim under §101.3 regardless of how confident the output sounds, and blocks Gate B until resolved.
  3907→
  3908→## 101.7 Severity-Scored Defect Log (CI-007)
  3909→
  3910→Not every issue found in Gate B halts a phase — but nothing found may be silently dropped. Every defect surfaced during Gate B is logged and scored:
  3911→
  3912→| Severity | Definition | Effect on phase completion |
  3913→|---|---|---|
  3914→| Blocker | Violates §0's non-negotiable contract, causes data loss, security exposure, or a non-functional critical path | Phase cannot be marked complete until resolved |
  3915→| Major | Functional gap against acceptance criteria, or a regression in previously working behavior | Must be resolved, or explicitly deferred with an owner sign-off recorded in the phase report |
  3916→| Minor | Cosmetic, non-blocking, or low-impact issue | Logged; does not block phase completion, but must not silently disappear from the record |
  3917→
  3918→This log feeds Definition of Done item 13 (§51) and the Production Readiness Checklist (§52) directly — a phase or a production launch cannot claim a clean bill of health while an open Blocker or unresolved Major sits outside this log.
  3919→
  3920→## 101.8 Cross-Phase Consistency Check (CI-008)
  3921→
  3922→Because phases in §50 build sequentially, an earlier "done" phase can silently drift out of true as later phases change shared contracts, types, or provider behavior. At a minimum every 3 phases, and always before the Production Launch Gate (§89):
  3923→
  3924→1. Re-run the applicable Gate B checks (§101.2) against every previously completed phase, not only the current one.
  3925→2. Confirm shared contracts (types, provider interfaces, API shapes) that earlier phases depended on have not silently changed underneath them.
  3926→3. Log any drift found as a defect under CI-007, scored by actual impact — a drifted contract that still functions correctly is not automatically a Blocker.
  3927→
  3928→## 101.9 Self-Report Audit Clause (CI-009)
  3929→
  3930→The agent's own claim that a gate passed is not self-verifying. A phase report claiming Gate B success must include enough raw evidence — per the Gate B evidence log (§101.2, step B7) — that a human or an independent process could check the claim without re-doing the work from scratch. An assertion of "tests pass" with no attached test output, or "verified against the repo" with no cited file state, does not meet this bar and is treated as an unverified self-report, not a completed phase.
  3931→
  3932→## 101.10 Retry Cost Accounting (CI-010)
  3933→
  3934→Re-derivation attempts under CI-005 are not free — GPU inference and provider API calls consumed during a failed attempt are real cost per §57. Each re-derivation attempt must log its incurred cost (video/voice/lip-sync/GPU/storage/bandwidth, as itemized in §57) against the requirement ID it was attempting. If a single requirement's cumulative retry cost becomes disproportionate to its scope before the three-attempt ceiling (§101.5) is reached, this is itself a signal to escalate early rather than continue spending toward the ceiling.
  3935→
  3936→## 101.11 Tamper-Evident Audit Trail (CI-011)
  3937→
  3938→The Gate B evidence log (§101.2) and the Severity-Scored Defect Log (§101.7) must be append-only, consistent with the structured-logging rules in §34. A phase must not be quietly re-marked complete, and a logged defect must not be quietly removed, without a visible corrective entry explaining the change. The audit trail exists so that "this was verified" is a checkable historical claim, not a mutable status field.
  3939→
  3940→## 101.12 Cross-Session Handoff Protocol (CI-012)
  3941→
  3942→If a different agent session or a different agent instance picks up a phase mid-stream, it must not trust the prior session's in-progress claims at face value. It must run Gate A (§101.2) fresh against the repository's actual current state before continuing — the same discipline CI-005 requires after a failed attempt applies here, with the session boundary itself as the trigger, not only an explicit failure.
  3943→
  3944→## 101.13 Definition of "Verified" for External Claims (CI-013)
  3945→
  3946→A claim about an external provider, API, model capability, or third-party service is only eligible for the `VERIFIED` label under §101.3 if the source URL and the date it was checked are both recorded, consistent with the research-recording format already required by §62. A claim with no citable source and date is `ASSUMED` at best, never `VERIFIED`, regardless of how standard or well-known the claim seems.
  3947→
  3948→## 101.14 PRD-Drift Check (CI-014)
  3949→
  3950→Across a long build, shipped code can silently diverge from this document without any single phase appearing to violate it. Before the Production Launch Gate (§89), and periodically per §101.8, the agent must reconcile the actual shipped system against this PRD section by section and report any divergence explicitly — whether the divergence is a regression that must be fixed, or a deliberate, approved deviation that should instead update this document via an ADR (§81). Silent divergence in either direction is not an acceptable end state.

  4007→Required product behavior, regardless of what verification finds for each platform:
  4008→
  4009→1. **Detect** in-app browser context on load (a `VERIFIED`, tested detection method — not a guessed user-agent string). Since Signal and parts of the Telegram flow may not present an in-app-browser context at all, detection logic must not assume every referring app behaves the same way.
  4010→2. **Attempt** the native realtime flow first if camera/mic access is actually available in that context. Given 102.1.1–102.1.2, expect this to succeed by default for Signal and the Telegram `openLink` path, and to need the fallback more often for Facebook and (assumed) WhatsApp.
  4011→3. **Fail gracefully and specifically** if it is not — per the UX failure standard in §58, not a generic error: e.g. *"This app's built-in browser blocks camera access. Tap ⋯ and choose 'Open in Browser' to continue."* Never a frozen permission prompt or an unexplained black screen (§87).
  4012→4. **Never silently degrade to a fake/stub camera feed** to avoid the error state — this would violate Contract items 7 and 9 in §0.

Findings for Zangi in particular start from zero and must be established from direct testing, not inferred from any other platform in this table.

  4017→
  4018→Recordings (§21) intended for re-sharing to social platforms must support the aspect ratios, resolutions, and duration constraints those platforms actually currently accept. The agent must research and confirm current specs (per §62) rather than hardcode remembered values, since these change per platform over time. At minimum, verify and support:
  4019→
  4020→| Format class | Typical use | Verify before hardcoding |
  4021→|---|---|---|
  4022→| Vertical (9:16) | Reels/Shorts/Stories-style short-form | Current max resolution, max duration, codec/container accepted |
  4023→| Square (1:1) | Feed posts | Same |
  4024→| Horizontal (16:9) | Traditional feed/YouTube-style | Same |
  4025→
  4026→Requirements:
  4027→
  4028→- The Recording Engine (§21) must support exporting the same captured session at multiple target aspect ratios without re-running AI inference — a crop/reframe/export step, not a re-transformation.
  4029→- Export presets are configuration data, not hardcoded constants buried in UI code, so they can be updated as platform specs change without a full redeploy (consistent with the Feature Flags philosophy in §42).
  4030→- Never claim an export is "optimized for [Platform]" without the underlying spec being `VERIFIED` per §101.13.

  4040→## 102.4 Desktop + Mobile Parity Reaffirmation (SOC-004)
  4041→
  4042→This section adds social/in-app-browser coverage on top of — and never as a replacement for — the Mobile-First Engineering Requirement already defined in §71–§76. To be explicit:
  4043→
  4044→- Every capability in the Feature Matrix (§5) must have a defined behavior on desktop, standalone mobile browser, and in-app/embedded mobile browser — three states, not two.
  4045→- Where in-app browser constraints make a full realtime capability impossible (e.g. no `getUserMedia`), the required response is the graceful degradation and clear redirect defined in §102.1 — not silently shipping a desktop-only product and calling it cross-platform.
  4046→- The Responsive Design breakpoints (§74) and Touch Interaction requirements (§75) apply identically whether the surface is a standalone browser or an in-app browser tab.
  4047→- This requirement is added to the Requirement Traceability Matrix (§80) and the Production Readiness Checklist (§52) as below.
