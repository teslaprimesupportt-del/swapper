# 1. EXECUTIVE PRODUCT DEFINITION

## 1.1 Product

A browser-first realtime AI media studio where a user can open a camera and microphone, choose a visual transformation and voice transformation, and see/hear the transformed result continuously with low latency.

The product is not a conventional video generator.

It is a **realtime interactive media system**.

Primary pipeline:

```text
Camera ─┐
        ├──> Capture ──> Realtime Media Transport ──> Session Gateway
Mic ────┘                                      │
                                               ├──> Video AI Pipeline
                                               ├──> Voice AI Pipeline
                                               ├──> Lip-Sync Pipeline
                                               └──> Control/Prompt Pipeline
                                                        │
                                                        ▼
                                                Synchronization Engine
                                                        │
                                                        ▼
                                               Output Media Stream
                                              /        |         \
                                         Browser   Recorder    Streaming
```

# 4. CORE USER JOURNEYS

## Journey A — First realtime session

1. User opens Studio.
2. Browser requests camera/microphone permissions.
3. Device selection appears.
4. Local preview starts immediately.
5. User selects a transformation.
6. Backend creates a short-lived realtime session token.
7. WebRTC session establishes.
8. AI provider connection establishes.
9. Output begins.
10. Metrics appear.
11. User can change transformation without leaving the session.

## Journey B — Voice changer

1. User enables microphone.
2. Audio capture begins.
3. Noise suppression and preprocessing run.
4. Audio is streamed.
5. Voice conversion processes the stream.
6. Converted audio returns.
7. Output is synchronized with video.
8. User can switch voice presets during the session.

## Journey C — Reference transformation

1. User uploads reference image.
2. Backend validates and stores it temporarily.
3. Reference is converted to a secure temporary URL/provider asset.
4. User enters prompt.
5. Transformation request is compiled.
6. Realtime session receives the update.
7. Output changes without restarting unnecessarily.

## Journey D — Network failure

1. WebRTC connection degrades.
2. Client detects quality degradation.
3. UI displays reconnecting state.
4. Session coordinator attempts bounded reconnection.
5. Existing session state is restored if possible.
6. If unavailable, provider failover/degraded mode activates.
7. User receives a clear status.

## 19.1 Voice Clone Verification Requirement (VOICE-CONSENT-001)

This subsection converts the general "must include consent/authorization controls" requirement in §59 into concrete, implementable verification steps. It is mandatory for any feature that creates a `VoicePreset` from a user-supplied voice sample (a clone), as distinct from a purely synthetic/built-in preset.

A cloned voice may not be created or activated for use until all of the following pass:

| Step | Requirement |
|---|---|
| Rights attestation | The uploading user affirmatively attests, per clone, that the voice belongs to them or that they hold documented rights/consent to clone it. Store this attestation as an immutable record tied to the `VoicePreset` row, not just a one-time checkbox at signup. |
| Liveness/active-consent capture | Require the source sample to be captured live within the product (e.g. read a randomized on-screen consent phrase), rather than accepting an arbitrary pre-recorded upload with no provenance. This raises the bar against cloning a voice the uploader does not control. |
| Consent artifact retention | Retain the consent capture (audio + attestation + timestamp) as an auditable artifact under the retention policy in §41, independent of the derived voice model itself. |
| Revocation path | The consenting individual (if different from the account holder, e.g. an authorized third party) must have a documented path to revoke consent, which immediately disables the associated `VoicePreset`. |
| Abuse/impersonation review | Cloned-voice presets are subject to the moderation/abuse-control requirements referenced in §26, with a defined escalation path for reported impersonation. |

`UNVERIFIED` claims about what a specific competitor product does or does not support (§101.3) must never be used to justify weakening this requirement. This gate exists independent of what any other product implements, per Contract item 19 in §0.

# 24. BILLING ARCHITECTURE

Usage must be server-authoritative.

Never bill based solely on client-reported seconds.

Record immutable usage events.

Example:

```text
session_started
video_second_consumed
audio_second_consumed
recording_storage_consumed
stream_started
session_ended
```

A billing service aggregates events.

## 24.1 Owner/Internal Billing Exemption (BILL-001)

The platform must support a role-scoped billing exemption for internal/owner accounts, without weakening the server-authoritative usage model above.

Requirements:

- `users.role` (§23) includes an internal tier (e.g. `owner`, `internal`) distinct from standard `user`/`admin` roles.
- A per-account flag — e.g. `billingExempt: boolean` — determines whether usage events for that account are invoiced. This must be a data-level flag checked server-side, never a client-side or UI-level bypass.
- **Usage events are still recorded for exempt accounts.** Exemption affects invoicing only, not metering. The owner's real GPU/provider cost is not free to the business — it must still flow through `usage_events` and the cost model in §57 so actual spend stays visible.
- Exemption must be auditable: every exempt session is logged in `audit_logs` (§23) with actor, timestamp, and cost basis, so "free for me" never becomes an untracked liability.
- Exemption must not bypass the abuse/quota controls in §57 (max session duration, concurrency limits) — an unmetered account is not an unlimited one; without a ceiling, a compromised or misused owner session can still generate runaway provider cost.
- Feature flag: `billing_enforcement` (extends §42) is evaluated per-account, not globally, so standard pay-as-you-go billing for all other users is unaffected by the owner exemption.

Every other account remains on the standard pay-as-you-go usage-event ledger defined above.

# 101. CODE INTEGRITY AND CONTINUOUS EXECUTION PROTOCOL (CI-CEP)

This section is binding on every phase defined in §50 and every acceptance gate defined in §51 and §52. It supersedes any earlier instruction that could be read as permission to produce shallow, generic, or unverified code, or to abandon a phase before its acceptance criteria are met. Where this section and an earlier section conflict on execution discipline, this section governs.

Requirement IDs introduced here (`CI-xxx`) must be added to the Requirement Traceability Matrix in §80 like any other requirement.

## 101.1 Definition: Generic/Sloppy Output (CI-001)

Output is classified **NON-CONFORMANT** if any of the following are true. Non-conformant output cannot be reported as part of a completed phase under §51.

| Class | Definition |
|---|---|
| Untraced boilerplate | Code copied from a generic pattern without being adapted to this repository's actual types, contracts, and provider-abstraction layers (§13, §70) |
| Unverified plausibility | Code that "looks correct" but was not checked against the real current state of the files it touches |
| Placeholder-as-final | TODOs, stubs, hardcoded fixtures, or fake success paths (violates Contract items 7–9 in §0) present in a path reported as complete |
| Silent scope narrowing | Code that satisfies the literal wording of a requirement while missing its functional intent |
| Orphaned change | Code with no traceable requirement ID (§80) or ADR (§81) justifying why it exists |

Every artifact the agent writes must cite the requirement ID(s) and/or ADR ID(s) it implements. A change with no traceable justification is itself a defect.

## 101.2 Verification Gate (CI-002)

Every unit of work passes through two mandatory checkpoints. Neither may be skipped or merged into one.

**Gate A — Pre-Implementation**

| Step | Action |
|---|---|
| A1 | Inspect actual current repository state for every file to be touched (§0 item 2) |
| A2 | Reconcile intended change against real structure, types, and contracts — not memory of a similar system |
| A3 | Classify every non-trivial claim per the Zero-Guess Protocol (§101.3) before writing code that depends on it |

**Gate B — Post-Implementation**

| Step | Action |
|---|---|
| B1 | Re-read every changed file as written to disk, not as drafted |
| B2 | Check against the phase's stated `ACCEPTANCE CRITERIA` (§54) |
| B3 | Check against every PRD section the change implements |
| B4 | Verify integration points — types, imports, config keys, provider contracts — actually resolve |
| B5 | Verify no previously passing behavior regressed (§0 item 3) |
| B6 | Run the applicable tier of §38 tests before the phase may be reported complete |
| B7 | Produce a Gate B evidence log — commands run, raw output, files diffed, tests executed with results — and attach it to the phase report (§54). A self-report of "Gate B passed" with no attached evidence does not satisfy B7 (see §101.9). |

Code is not "done" because it was generated. It is done only after passing Gate B. A phase report (§54) submitted without an attached Gate B evidence log is itself non-conformant and cannot satisfy Definition of Done item 12 (§51).

## 101.3 Zero-Guess Protocol (CI-003)

Every non-trivial factual claim underlying a piece of code must be classified before that code is written:

| Label | Meaning | Permitted basis |
|---|---|---|
| `VERIFIED` | Confirmed against the actual repository, actual official documentation (§62), or an actual executed check | Direct inspection only |
| `ASSUMED` | Not yet confirmed; logged to the Assumption Register (§82) with confidence and impact-if-wrong | Explicit, tracked, reversible |
| `UNVERIFIED` | Flagged as such in the response; blocks phase completion until resolved | Never a basis for shipped code |

Forbidden basis for writing code: pattern-matching to "what this API/library/file usually looks like" and presenting it as fact. This applies to API signatures, provider behavior, library interfaces, configuration keys, file paths, existing repository structure, and data shapes — no exceptions for "just one line." A single fabricated line is treated with the same severity as a fabricated subsystem, because the failure mode (undetected incorrect assumption in shipped code) is identical.

**Fallout rule:** if an `ASSUMED` claim logged to the Assumption Register (§82) is later proven wrong, this is not a footnote-only correction. It automatically triggers a Non-Regressive Recovery Protocol re-derivation (§101.5) for the assumption itself and for every downstream artifact that was built depending on it, traced via the requirement/ADR IDs those artifacts cited under CI-001. An ADR update alone does not close the loop — the affected code must be re-verified against the corrected fact.

## 101.4 Continuous Execution Guarantee (CI-004)

Once a phase's scope is confirmed (§50, §54), the agent drives it to its stated acceptance criteria without discretionary interruption. The distinction that governs this section is **blocking condition** vs. **discretionary halt**:

| Condition | Classification | Required response |
|---|---|---|
| Failing test, compile error, unexpected repo state | Expected operating condition | Diagnose and fix; continue (per §53's BREAK→FIX→VERIFY loop) |
| Ambiguous product decision with no safe default | Genuine blocker | Surface immediately per §77/§78; do not silently choose and do not silently stall |
| Missing credential/external dependency outside agent's control | Genuine blocker | Surface immediately, name exactly what is needed, continue on all unblocked work in parallel |
| Fatigue-style stopping, scope feels large, task feels tedious | Discretionary halt | **Prohibited.** Not a valid reason to pause, defer, or abandon a phase |
| Partial progress feels "good enough" | Discretionary halt | **Prohibited.** Only the stated acceptance criteria define done (§51) |

Surfacing a genuine blocker is reporting, not stopping — the agent states what it needs and keeps working on everything not gated by that blocker. Silence, indefinite pausing, or unexplained abandonment mid-phase are not available responses under this protocol.

## 101.5 Non-Regressive Recovery Protocol (CI-005)

If a phase's acceptance criteria are not met by the end of an attempt, the failure is handled as data, not as a stopping point:

1. **Report honestly** — state exactly what passed Gate B, what failed, and why, using the `KNOWN LIMITATIONS` field of §54's response format. Never mark a failed phase complete.
2. **Do not leave a half-verified state as the baseline** — an incomplete attempt must not be left implicit for a future attempt to inherit unexamined.
3. **Re-derive from ground truth on the next attempt** — re-run Gate A against the repository's actual current state rather than resuming from the previous attempt's assumptions. If the previous attempt's partial work is inconsistent with what Gate A now finds, treat it as unverified and rebuild the affected portion rather than patching over it.
4. **Do not repeat the same unverified work indefinitely** — each retry must be demonstrably different from the last: a new fact was verified, a blocker was resolved, an assumption was corrected. A retry that changes nothing about what was previously wrong is not a valid retry.
5. **Retry ceiling** — after **three** re-derivation attempts on the same requirement ID without meeting acceptance criteria, the requirement automatically escalates to a `BLOCKED — HUMAN DECISION REQUIRED` state rather than attempting a fourth retry. Escalation must state: what was tried across all three attempts, what changed each time, and the specific decision or resource needed to proceed. A subsystem-specific ADR (§81) may set a different ceiling with explicit justification; absent one, three is the default.

The objective of CI-005 is that every attempt starts from verified ground truth rather than compounding an earlier, unverified mistake — not endless unmonitored looping, and not silent abandonment.

## 101.6 Hallucinated-Dependency Check (CI-006)

A distinct and common failure mode from general guessing (§101.3): inventing a dependency that does not exist. Before any import, package install, API endpoint, or config flag is used, the agent must confirm — not assume — that it is real:

| Dependency type | Required confirmation |
|---|---|
| npm/pip/other package | Confirm the package name, version, and published API actually exist in the registry (§48's package boundaries apply) — not "a package like this probably exists" |
| External API endpoint | Confirm the endpoint exists in current official documentation (§62), not a remembered or inferred URL pattern |
| Config/environment flag | Confirm the flag is real for the specific library/service version in use, not a plausible-sounding name |
| Framework API/method | Confirm the method exists on the specific version pinned in this repository, not a version remembered from training |

A hallucinated dependency is classified as an `UNVERIFIED` claim under §101.3 regardless of how confident the output sounds, and blocks Gate B until resolved.

## 101.7 Severity-Scored Defect Log (CI-007)

Not every issue found in Gate B halts a phase — but nothing found may be silently dropped. Every defect surfaced during Gate B is logged and scored:

| Severity | Definition | Effect on phase completion |
|---|---|---|
| Blocker | Violates §0's non-negotiable contract, causes data loss, security exposure, or a non-functional critical path | Phase cannot be marked complete until resolved |
| Major | Functional gap against acceptance criteria, or a regression in previously working behavior | Must be resolved, or explicitly deferred with an owner sign-off recorded in the phase report |
| Minor | Cosmetic, non-blocking, or low-impact issue | Logged; does not block phase completion, but must not silently disappear from the record |

This log feeds Definition of Done item 13 (§51) and the Production Readiness Checklist (§52) directly — a phase or a production launch cannot claim a clean bill of health while an open Blocker or unresolved Major sits outside this log.

## 101.8 Cross-Phase Consistency Check (CI-008)

Because phases in §50 build sequentially, an earlier "done" phase can silently drift out of true as later phases change shared contracts, types, or provider behavior. At a minimum every 3 phases, and always before the Production Launch Gate (§89):

1. Re-run the applicable Gate B checks (§101.2) against every previously completed phase, not only the current one.
2. Confirm shared contracts (types, provider interfaces, API shapes) that earlier phases depended on have not silently changed underneath them.
3. Log any drift found as a defect under CI-007, scored by actual impact — a drifted contract that still functions correctly is not automatically a Blocker.

## 101.9 Self-Report Audit Clause (CI-009)

The agent's own claim that a gate passed is not self-verifying. A phase report claiming Gate B success must include enough raw evidence — per the Gate B evidence log (§101.2, step B7) — that a human or an independent process could check the claim without re-doing the work from scratch. An assertion of "tests pass" with no attached test output, or "verified against the repo" with no cited file state, does not meet this bar and is treated as an unverified self-report, not a completed phase.

## 101.10 Retry Cost Accounting (CI-010)

Re-derivation attempts under CI-005 are not free — GPU inference and provider API calls consumed during a failed attempt are real cost per §57. Each re-derivation attempt must log its incurred cost (video/voice/lip-sync/GPU/storage/bandwidth, as itemized in §57) against the requirement ID it was attempting. If a single requirement's cumulative retry cost becomes disproportionate to its scope before the three-attempt ceiling (§101.5) is reached, this is itself a signal to escalate early rather than continue spending toward the ceiling.

## 101.11 Tamper-Evident Audit Trail (CI-011)

The Gate B evidence log (§101.2) and the Severity-Scored Defect Log (§101.7) must be append-only, consistent with the structured-logging rules in §34. A phase must not be quietly re-marked complete, and a logged defect must not be quietly removed, without a visible corrective entry explaining the change. The audit trail exists so that "this was verified" is a checkable historical claim, not a mutable status field.

## 101.12 Cross-Session Handoff Protocol (CI-012)

If a different agent session or a different agent instance picks up a phase mid-stream, it must not trust the prior session's in-progress claims at face value. It must run Gate A (§101.2) fresh against the repository's actual current state before continuing — the same discipline CI-005 requires after a failed attempt applies here, with the session boundary itself as the trigger, not only an explicit failure.

## 101.13 Definition of "Verified" for External Claims (CI-013)

A claim about an external provider, API, model capability, or third-party service is only eligible for the `VERIFIED` label under §101.3 if the source URL and the date it was checked are both recorded, consistent with the research-recording format already required by §62. A claim with no citable source and date is `ASSUMED` at best, never `VERIFIED`, regardless of how standard or well-known the claim seems.

## 101.14 PRD-Drift Check (CI-014)

Across a long build, shipped code can silently diverge from this document without any single phase appearing to violate it. Before the Production Launch Gate (§89), and periodically per §101.8, the agent must reconcile the actual shipped system against this PRD section by section and report any divergence explicitly — whether the divergence is a regression that must be fixed, or a deliberate, approved deviation that should instead update this document via an ADR (§81). Silent divergence in either direction is not an acceptable end state.

# 102. CROSS-PLATFORM AND SOCIAL DISTRIBUTION COMPATIBILITY

This section makes explicit a requirement that was previously implicit: the product must work reliably for real users on the surfaces they actually arrive from and share to — which for a camera/mic-based creative tool means both native desktop/mobile browsers **and** the in-app browsers embedded in major social apps, plus export formats that fit those platforms' actual current specs.

Per §84 (Current-Documentation Rule), none of the platform-specific behaviors below may be hardcoded from memory. In-app browser permission handling, embed policies, RTMP ingest availability, and export specs all change without notice. Every claim in this section's tables must be classified `VERIFIED` / `ASSUMED` / `UNVERIFIED` per §101.3 and re-checked before Production Launch (§89), not assumed to still hold from whenever this document was written.

## 102.1 In-App Browser Compatibility Requirement (SOC-001)

Camera- and microphone-based web apps are frequently opened from links shared inside social/messaging apps, which render the page in a constrained in-app (embedded) browser rather than the user's default browser. This is a distinct environment from the standalone mobile browsers already covered in §71–§76 and must be tested separately, not assumed to behave the same.

**Target platform scope for this build:** WhatsApp, Facebook, Zangi, Telegram, Signal. This replaces a broader initial draft list and is the authoritative scope for SOC-001 verification effort.

### 102.1.1 Verified research findings (per CI-013, §101.13)

These findings are `VERIFIED` per §101.3 — sourced, dated, and directly relevant to this product's target platform list:

| Finding | Source | Date checked | Confidence |
|---|---|---|---|
| Signal has no in-app browser. Links tapped in Signal (iOS and Android) open in the device's external default browser, not an embedded WebView | Signal-iOS GitHub issue #4150 ("Links in Signal — Please give us choice of browser," discussing that links already open externally, just not in the user's preferred external browser) | 2026-08-15 | High — primary source (Signal's own issue tracker), corroborated by a second Signal-Android issue (#12347) discussing external link-opening behavior |
| On iOS, Telegram's Mini-App `openLink` method always opens links in the **external** browser, never Telegram's in-app browser — this is explicitly the opposite of Android, where the same call opens in-app by default | Telegram-iOS GitHub issue #1670 | 2026-08-15 | High — primary source (Telegram's own repository) |
| Separately, for an ordinary tapped link (not a Mini-App `openLink` call), Telegram on iOS generally uses `SFSafariViewController` rather than a raw `WKWebView` for its in-app browser view. `SFSafariViewController` is a materially different technical situation than the raw-`WKWebView` pattern documented in 102.1.1 below for Facebook — it runs as Safari's own view controller rather than an embedded web engine without Safari's privileges | Cross-referenced from Telegram browser-behavior documentation and the general SFSafariViewController vs. WKWebView distinction | 2026-08-15 | Medium — the general architectural distinction is well-established; this response did not find a primary source confirming `getUserMedia` parity specifically for Telegram's `SFSafariViewController` instance |
| `getUserMedia` in raw WKWebView-based in-app browsers (the pattern Facebook's in-app browser follows) has a long-documented history of failing or behaving inconsistently versus standalone Safari — including reports as recent as iOS 17.5/17.6 and 18 simulators, indicating this is an ongoing issue, not one that was fully resolved after the original 2019–2021-era reports | WebKit Bugzilla #208667; Apple Developer Forums threads 734363, 750254, 770737 | 2026-08-15 | High — primary sources, spanning multiple iOS versions over several years |
| Facebook deliberately keeps outbound links inside its own in-app browser rather than handing off to the system browser, as a retention mechanism — this is the default experience for a shared link, not an edge case | Apple Community discussion thread 742526; independent confirmation from a link-routing vendor's documentation | 2026-08-15 | Medium — consistent user/developer reports, not an official Meta statement |

**What this response could not verify:**

- **WhatsApp's specific in-app browser engine.** WhatsApp is widely believed in web-developer communities to use a WKWebView-based in-app browser on iOS, consistent with the general Meta-family pattern seen in Facebook — but this response did not find a primary source confirming that specifically for WhatsApp's current version. Treat as `ASSUMED`, not `VERIFIED`, until device-tested.
- **Zangi.** No usable information was found on Zangi's in-app browser behavior, engine, or WebRTC support at all — it is a smaller/less-documented app and this response found nothing authoritative. This is not evidence that it works or doesn't; it means it must be device-tested from a position of zero prior information, and should not be assumed to follow the Meta-family (Facebook/WhatsApp) pattern or the Signal/Telegram pattern.

### 102.1.2 Risk tier and required build priority

Given the above, the platforms in scope for this build fall into three distinct risk tiers rather than one uniform risk — this should directly inform build and test order:

| Platform | Risk tier | Basis |
|---|---|---|
| Signal | Low | No in-app browser exists; behaves like a standalone browser visit (102.1.1, high confidence) |
| Telegram | Low–Medium, path-dependent | External browser for Mini-App `openLink` calls (high confidence); ordinary tapped links likely use `SFSafariViewController` on iOS, a materially safer engine than raw WKWebView, though not independently confirmed for `getUserMedia` specifically (medium confidence). Android in-app behavior is a separate case requiring its own test. |
| Facebook | High | Directly documented WKWebView-pattern history of `getUserMedia` failures; deliberately does not hand off to external browser by default |
| WhatsApp | High, `ASSUMED` | Believed to follow the same Meta-family WKWebView pattern as Facebook, but not independently confirmed this session — treat as high-risk until device-tested, not as an assumption resolved in the product's favor |
| Zangi | Unknown | No information found; requires ground-up device testing with no prior assumption in either direction |

Minimum required test/verification matrix — extends the Mobile Device Capability Matrix in §72:

| Surface | Risk tier | Must verify (current, per §62/§84) |
|---|---|---|
| WhatsApp in-app browser (iOS + Android) | High, `ASSUMED` engine | `getUserMedia` availability with combined audio+video, permission prompt behavior, whether an explicit escape to native Safari/Chrome exists |
| Facebook in-app browser (iOS + Android) | High | Same as above |
| Zangi in-app browser or link-handling behavior (iOS + Android) | Unknown | Same as above, plus first establish whether an in-app browser exists at all |
| Telegram — Mini-App `openLink` path (iOS) | Low (confirmed external) | Confirm current behavior still matches 102.1.1's finding |
| Telegram — ordinary tapped link (iOS) | Low–Medium | Confirm `SFSafariViewController` is actually in use and that `getUserMedia` with combined audio+video works in it |
| Telegram — in-app browser (Android) | Medium, untested | Android opens in-app by default per 102.1.1; verify `getUserMedia` behavior directly, do not assume parity with the iOS finding |
| Signal (iOS + Android) | Low | Confirm links still open externally in the current app version before relying on this |

Required product behavior, regardless of what verification finds for each platform:

1. **Detect** in-app browser context on load (a `VERIFIED`, tested detection method — not a guessed user-agent string). Since Signal and parts of the Telegram flow may not present an in-app-browser context at all, detection logic must not assume every referring app behaves the same way.
2. **Attempt** the native realtime flow first if camera/mic access is actually available in that context. Given 102.1.1–102.1.2, expect this to succeed by default for Signal and the Telegram `openLink` path, and to need the fallback more often for Facebook and (assumed) WhatsApp.
3. **Fail gracefully and specifically** if it is not — per the UX failure standard in §58, not a generic error: e.g. *"This app's built-in browser blocks camera access. Tap ⋯ and choose 'Open in Browser' to continue."* Never a frozen permission prompt or an unexplained black screen (§87).
4. **Never silently degrade to a fake/stub camera feed** to avoid the error state — this would violate Contract items 7 and 9 in §0.

Findings above establish the general pattern and justify the risk-tier prioritization; they do not substitute for live, per-platform, per-version device testing, which remains mandatory before this requirement is marked satisfied — this is a live compatibility surface that changes without notice, not a one-time assumption. Findings for Zangi in particular start from zero and must be established from direct testing, not inferred from any other platform in this table.

## 102.2 Social Export/Share Specification (SOC-002)

Recordings (§21) intended for re-sharing to social platforms must support the aspect ratios, resolutions, and duration constraints those platforms actually currently accept. The agent must research and confirm current specs (per §62) rather than hardcode remembered values, since these change per platform over time. At minimum, verify and support:

| Format class | Typical use | Verify before hardcoding |
|---|---|---|
| Vertical (9:16) | Reels/Shorts/Stories-style short-form | Current max resolution, max duration, codec/container accepted |
| Square (1:1) | Feed posts | Same |
| Horizontal (16:9) | Traditional feed/YouTube-style | Same |

Requirements:

- The Recording Engine (§21) must support exporting the same captured session at multiple target aspect ratios without re-running AI inference — a crop/reframe/export step, not a re-transformation.
- Export presets are configuration data, not hardcoded constants buried in UI code, so they can be updated as platform specs change without a full redeploy (consistent with the Feature Flags philosophy in §42).
- Never claim an export is "optimized for [Platform]" without the underlying spec being `VERIFIED` per §101.13.

## 102.3 Social Streaming Destination Presets (SOC-003)

Extends the Streaming Engine (§22) with named destination presets for major live platforms, subject to the same verification discipline as §98's provider research:

- For each candidate destination (e.g. common RTMP-ingest platforms), verify current: RTMP/SRT ingest availability, authentication method, terms of service around third-party client tools, and any rate/quality limits — per the API research template in §68.
- Store destination credentials encrypted per §22 and §26; never hardcode a platform's ingest URL without verifying it is still current.
- A destination preset that cannot be verified is marked `UNVERIFIED` and shipped behind a feature flag (§42) until confirmed, not enabled by default on assumption.

## 102.4 Desktop + Mobile Parity Reaffirmation (SOC-004)

This section adds social/in-app-browser coverage on top of — and never as a replacement for — the Mobile-First Engineering Requirement already defined in §71–§76. To be explicit:

- Every capability in the Feature Matrix (§5) must have a defined behavior on desktop, standalone mobile browser, and in-app/embedded mobile browser — three states, not two.
- Where in-app browser constraints make a full realtime capability impossible (e.g. no `getUserMedia`), the required response is the graceful degradation and clear redirect defined in §102.1 — not silently shipping a desktop-only product and calling it cross-platform.
- The Responsive Design breakpoints (§74) and Touch Interaction requirements (§75) apply identically whether the surface is a standalone browser or an in-app browser tab.
- This requirement is added to the Requirement Traceability Matrix (§80) and the Production Readiness Checklist (§52) as below.
